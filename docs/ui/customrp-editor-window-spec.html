CustomRP Editor Window — Redesign Spec

A ground-up rebuild of the 480 × 620 grouped Form. Two-tier row system, one fixed label column, one section-header treatment, and no control ever sharing a line with a full-length URL. Every dimension below maps to SwiftUI/AppKit primitives — no custom drawing, no Canvas, no hand-rolled layout.

1:1 mocks · light + dark 480 × 620 minimum 560 × 720 recommended 22 pt control height 13 pt body · 11 pt secondary
01

Overview & recommendation

The window keeps its content and its grouped-Form character. What changes is the grid underneath it: a fixed label column, a second stacked tier for long fields, and a single consistent home for helper text and actions.

Recommend 560 × 720 as the default. At 480 pt the card interior is 428 pt; after the 132 pt label column a standard field gets 288 pt — enough for short values but not for the two URL rows, which is why the old window truncated them. At 560 pt every inline field gets 368 pt and the squeeze disappears entirely. Keep 480 × 600 as the minimum so the window still behaves on a 13" MacBook in Split View.

What changed and why

One row per problem from the review. “Metric” is the number that proves the fix — it is what the implementer should hold the build to.

#Old layoutNew layoutMetric that makes it work
1 “Time” and “Images” headers sat outside their cards and the first card had none, so the top edge read as unfinished. Every section opens with the same 11 pt semibold header, 6 pt above its card. The Connection card is now headed “Connection”. 1 header style across 5 sections; header→card gap fixed at 6 pt; 20 pt between sections.
2 Explanations appeared inside cards, above controls, and wedged between a picker and a date picker. All helper text is 11 pt secondary and lives in exactly two places: the card’s lead note (whole-card scope) or a footer row directly under the field it describes. 1 typographic treatment (11 pt, secondaryLabel); 4 pt gap to the field above.
3 “Load asset names” sat inside the data card, mixed in with editable fields. Row-level actions (Upload…, Assets, Add button) sit in a dedicated trailing action row inside their group; card-wide actions sit in the action row under the card’s fields. No action ever shares a row with a data field; 8 pt between grouped buttons.
4 “Party current” / “Party max” were two loose fields side by side with no column or separation. One inline row: label “Party”, then two 46 pt numeric fields separated by a slash and closed by the 11 pt caption “current / max”. Both fields share one baseline and one left edge; 6 pt between them.
5 No fixed label column — label widths varied, so values did not line up and short labels pushed values toward the right edge. A single 132 pt label column, left-aligned, with an 8 pt gap; the control column takes the remainder. 132 pt fits the longest label (“Shown as (Discord app name)”) with room to spare; zero truncation.
6 Long label + full URL + “Upload…” forced onto one 480 pt line, so the URL was truncated and nearly uneditable. URL rows use the stacked tier: label above, full-width field, and the actions moved to their own row underneath. Field spans the full card interior — 428 pt at 480, 508 pt at 560; never below 288 pt.
7 The date picker rendered 9/ 1/2002, 17:25 — cramped, with odd spacing around the stepper. DatePicker(.field) goes full width in the stacked tier: calendar glyph, date, flexible spacer, time pinned right behind a hairline. One 22 pt control spanning 428/508 pt; time always right-aligned, 9 pt inset.
8 Link and optional text fields had no border or background, so an empty field was indistinguishable from a static label. Every editable field uses the same 22 pt bordered surface and a tertiary placeholder; read-only values render as plain text instead. 1 field surface for all inputs; 1 pt border at 17% black/white; 6 pt radius.
9 The 480 pt window was too narrow for the three-column rows it attempted. Three-column rows are gone. The layout allows at most two columns (label + control), and URL rows collapse to one. Max 2 columns per row; ≥ 288 pt for every inline control at the minimum size.

07

Rules

Non-negotiable behaviours the build is checked against.

  • Full keyboard access.

    Tab order follows visual order, top to bottom, footer buttons last. Every control shows a visible :focus-visible ring.

  • Empty optional fields look editable.

    Same 22 pt bordered surface as a filled field, with a tertiary placeholder — never a borderless line that reads as a static label.

  • URLs are fully readable.

    One full-width field in the stacked tier. Trailing actions move to their own row and never squeeze the field. No ellipsis on a key or link.

  • Labels never truncate.

    The 132 pt column fits the longest label; stacked labels get the full card width. If a label is added later, widen the column — do not clip it.

  • Disabled is visibly disabled.

    42% opacity plus a non-accent fill. The card keeps its height and layout so nothing jumps when a control enables.

  • “Competing in” looks intentional.

    The Time card stays in place with its controls dimmed and the note The “Competing” type cannot show timestamps. in the footer. It never collapses or disappears.

  • One primary action per view.

    Only the footer Apply is prominent. The Connection Apply stays bordered and “Save as New” is borderless.

  • Errors state the fix.

    Messages name the field and the limit, e.g. Button 1 label is 40 bytes; Discord allows 32. Never truncate a validation message.
